# Migration and Transition Qualification

## First separate the work

“Migration” can refer to different workstreams:

- course or content conversion;
- user, enrollment, completion or historical-data movement;
- integration replacement or redesign;
- authentication transition;
- reporting or analytics asset transition;
- product end-of-life transition;
- operational change and adoption.

These workstreams have different owners, tools, feasibility limits and acceptance criteria.

## Required discovery

- Source platform, version and export formats.
- Number and types of courses, files, question libraries and interactive objects.
- Historical records that must move versus records that can remain archived.
- Identity, user, enrollment and completion sources of truth.
- Integrations, authentication and external links that require replacement.
- Accessibility and copyright constraints.
- Required validation samples and acceptance owner.
- Freeze periods, academic or business blackout dates and continuity requirements.
- Customer capacity for cleanup, mapping, testing and decisions.

## Evidence rule

A successful migration example proves that a named customer completed a defined project. It does not establish that every source object can be converted, that effort is fixed or that disruption will be zero.

## Routing

- New-logo scope and project design: Implementation Services.
- Current-customer product or end-of-life transition: Transition Services through its current intake process.
- D2L Link workflow implementation: use the current prebuilt-versus-custom implementation source.
- Unclear feasibility or acceptance: request technical scoping before proposal language.

## Seller response to migration risk

“That concern is reasonable. Before we talk timing, we should separate content, data, integrations and change readiness, then identify what must be validated and who will accept it.”
